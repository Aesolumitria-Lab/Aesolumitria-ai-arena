# 引擎骨架

目的：下一道题开工时不必重新发明工程结构，只写规则。

**规则逻辑不复用，工程结构复用。** 不同题的单步结算没有相似之处，硬抽公共库只会抽出谁都不好用的中间层；真正可复用、又最耗时间的是下面的结构。

## 1. 五层结构

```
engine.cpp      规则本体，常驻进程，行协议，无随机无浮点
judge.py        进程管理、计时、协议校验、判罚、回放；不含任何规则
arena.hpp       选手可见状态 + 纯 helper
template.cpp    Starter：能编译、能跑完、不保证强
tools/          validate / bench / pack / leakcheck / calibrate 等
```

关键一条：**规则只能出现在 `engine.cpp` 里**。裁判若也实现规则，就会有两份实现、必然分歧，最后“本地能过、线上挂”。裁判只做四件事：拉起进程、读写协议、计时、判罚。场级结算（一场几局、换座、tiebreak）若放在裁判里，要专门测试。

## 2. 协议模板

三段式：`INIT`（一次，静态信息）、`TURN <t>`（每步，动态状态）、应答（一行，以步号开头）。

- 一行一条消息，`\n` 结尾；
- 应答必须以步号开头，迟到/重复的直接丢弃；
- 每步输出后 flush；
- stdout 只允许协议行，调试走 stderr。

状态用**绝对量**不用增量：比如“失效步号”而不是“剩余步数”。递减计数器在“当步是否生效”上必有歧义，两个实现各选一个回放就对不上。

一步问几个 bot 决定裁判结构：同时下令要收集多份指令再提交，超时分别记；交替激活每步问一个，但“无兵可动时推进步号”应放在引擎里，裁判只认 `next_seat` 之类的字段。

## 3. 状态哈希

用 FNV-1a 64 之类的固定算法，输入包含**所有会影响后续结算的字段**，输出 16 位十六进制。用途：golden 断言、回放重算、跨平台一致性、定位“从哪一步开始不同”。漏掉字段会让不同状态得到同一 hash，这类遗漏 golden 测试暴露不出来，只有回放对账时才炸。

## 4. 验收要点

- 边界测试全过；golden 至少数例；同序列跑两次 hash 一致；
- fuzz 要看**平均步数是否足够长**：随机动作下对局若很快结束，步数上限根本没被压到，“测试通过”不等于“测试有效”；
- `pack.py` 两次 sha256 一致，`leakcheck.py` 无失败；
- 基准档位单调（比胜负，不比分差）；
- **同名 bot 内战应接近平局**。对抗类题必须有换边/换座机制，否则先手优势会让同名内战一边倒。

## 5. 开工顺序

1. 先能回答：一句话、强制进攻时钟、基准分几档；
2. 用 12 节结构写 `RULES.md`，结算顺序编号；
3. 列边界用例，能自动验的先写断言；
4. 写 `engine.cpp`（只含规则）；
5. 写 `judge.py`（只含进程/计时/判罚）；
6. 写 Starter 与基准；
7. 跑 `validate`，再跑 `bench` 看梯度；
8. **看同名内战是否接近平局**，不接近先修公平性——这一步最容易被跳过，也最贵；
9. `pack` + `leakcheck`；
10. 把没解决的问题写进题目 `known-issues`。
