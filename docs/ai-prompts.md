# 提示词说明

本文讲为什么把造题工作拆成多个角色、每份提示词的写法要点。可直接使用的模板在 [`../prompts/`](../prompts/README.md)。

## 1. 为什么不能只写一条提示词

一条“帮我实现一个对战游戏”的提示词，通常得到：规则边写边改、代码与文档对不上；把完整状态发给 bot；用浮点、`rand()`、`unordered_map` 遍历导致不可复现；只测墙钟；基准太强或太弱；没有回放和 golden 用例；公开包混入私有内容。

所以拆成 6 个角色，每个只对一件事负责。

## 2. 角色与文件

| 角色 | 模板 | 输出 | 关键约束 |
|---|---|---|---|
| 出题人 | `prompts/set_problem.md` | 12 节 `RULES.md` 骨架、状态机、边界清单 | 不写代码，先让规则可判定 |
| 引擎 AI | `prompts/build_game.md` | 引擎、裁判、协议、测试、回放、工具接入 | 确定性、信息裁剪、CPU 预算 |
| 基准 AI | `prompts/build_anchor.md` | 多档隐藏基准 | 简单、可解释、可被击败 |
| 脚手架 AI | `prompts/build_starter.md` | 公开 Starter + SDK 头 | <300 行、合法、不泄漏 |
| 参赛模型 | `prompts/contestant_prompt.md` | 一个 `bot.cpp` | 限时、预算内、不联网 |
| 红队 AI | `prompts/red_team.md` | 按严重度排序的缺陷报告 | 只找问题，不改代码，换一个 AI |

顺序：

```
set_problem → 人工审规则 → build_game → build_anchor / build_starter → red_team → 冻结 → contestant_prompt
```

`build_anchor` 在 `build_game` 之后（基准要调用引擎模拟）；`build_starter` 在协议冻结之后；`red_team` 在打包之前。占位符（`{{GAME_ID}}` 等）发出前必须全部替换，见 `prompts/README.md`。

## 3. 两阶段工作流

**阶段 A：冻结规则（不写引擎）。** 产出 12 节 `RULES.md`、状态机、至少 25 条边界用例、参数表。验收：每条规则能回答“是/否”；每个动作有明确非法处理；每个随机源可追溯到 seed；每个“同时”有固定结算顺序。阶段 A 不通过，不进阶段 B，否则 AI 会在代码里替你猜规则。

**阶段 B：实现引擎。** 每个模块编译一次、每条规则加一个测试，最后真实运行验收命令并把输出写进报告。验收：测试全绿、fuzz 无崩溃、同 seed 同动作 hash 一致、座位镜像一致、`pack.py` 只含 `public/`、`leakcheck.py` 无失败、`bench.py` 计时有余量。

## 4. 引擎提示词的要点

- **角色**：写“引擎实现者，唯一目标是把冻结的 `RULES.md` 变成引擎”，而不是“资深游戏开发者”；不负责设计规则和平衡；
- **输入**：列出 `RULES.md`、`meta.json`、地图格式、协议样例；规则有歧义时写进 `DECISIONS.md`，选最保守解释，不要改 `RULES.md`；
- **硬约束**用“必须/禁止”：C++17 零警告；整数/定点；固定 seed PRNG；固定遍历顺序；单线程；禁网络、文件、环境变量、系统时间；每步 flush；调试只写 stderr；
- **交付物**给完整文件树和每个文件的职责；
- **结算顺序**逐条对应 `RULES.md`，代码里用注释标步骤；
- **协议**冻结，不加字段、不改顺序；
- **错误处理**用表格；不允许宽容解析；
- **测试**四类：golden、边界、性质（fuzz、镜像）、协议；
- **验收命令**可复制，要求真实执行并粘贴输出，失败修到通过，不伪造；
- **停止条件**：所有验收命令通过即停，不加功能。

写法技巧：给文件名不给方向；给结构体不给形容词；给黄金例子；给“不要做”清单；要求先写短 `PLAN.md`；要求每步可编译；用第二个 AI 红队；用 hash 冻结规则。

## 5. 基准提示词

基准不是“强 bot”。常见错误是让 AI“写一个尽可能强的 bot”，结果带搜索、带对手模型、带地图硬编码，导致分数挤在零附近、过拟合公开图、无法解释、自己超时。正确写法：简单、稳定、可解释、可被击败；不硬编码地图；不读隐藏信息；不超时；相邻档位可区分。若上档对下档胜率过高，降低能力而不是加规则。

## 6. Starter 提示词

Starter 是公开脚手架，不是基准。只需正确解析协议、每步输出合法动作、有一个很笨的策略、零警告、不含搜索/评估/地图硬编码/私有路径。常见错误：写得太强让选手直接提交就能中游；含 `if (map == ...)`；输出格式与协议不一致。

## 7. 参赛提示词

目标不是“写出最强 bot”，而是在限时内写出不崩、不超时、能得分的 bot。应包含：规则摘要、协议样例、编译与本地裁判命令、预算、禁止项、提交格式、常见坑，以及“先跑通再优化”的明确指令。参赛行为红线见 [contestant-rules.md](contestant-rules.md)。

## 8. 红队提示词

红队是找茬，不是重写。维度：确定性；信息泄漏；规则歧义；拖延/刷分；崩溃/超时；基准强度；回放复现；打包内容。输出按 P0–P3 排序，每条含位置、复现、影响、建议；没有复现的标为“待验证”；只报告，不改代码。

## 9. 反模式

| 反模式 | 正确做法 |
|---|---|
| “写一个对战游戏” | 先写 `RULES.md`，再实现 |
| “尽量确定性” | “禁止 float；固定遍历顺序” |
| “把完整状态发给 bot 让它自己过滤” | 引擎裁剪，bot 只收可见状态 |
| “写一个强基准” | “写一个简单、可被击败的基准” |
| “先写代码规则以后补” | 阶段 A 冻结规则 |
| “一次生成多个游戏” | 一次一个游戏 |
| “debug 输出到 stdout 方便” | 只写 stderr |
| “把基准源码发给选手当参考” | 只发 Starter，基准隐藏 |
