# 总览与设计原则

## 1. 背景

这个题库面向一种特定的比赛：**模型或人拿到同一份规则，在有限时间内写一个 bot，然后把 bot 放进同一个确定性赛场，用大量对局排出强弱**。

设计参考 [chen-006/meow-ai-arena](https://github.com/chen-006/meow-ai-arena)（MIT）的赛制。平台约束大致如下（具体数值以各题 `RULES.md` 为准）：

| 项目 | 约束 |
|---|---|
| 选手产出 | 一个独立 bot（官方模板为 C++17） |
| 编写时间 | 由各题 `prompt.md` / `README.md` 规定，只给规则、模板、本地裁判 |
| 每步预算 | CPU 时间（P01 为 50ms 基准，另有宿主系数，见 P01 `RULES.md` §15.2） |
| 首步预算 | 2s 墙钟宽限，含进程启动与第一次决策 |
| 判罚 | 超时 / 非法按题判罚；累计 3 次 fault 判负；崩溃直接判负 |
| 对局量 | 每个 bot 打大量对局，用 Bradley–Terry 或名次类口径评分 |
| 复现 | 固定种子、固定规则版本、固定引擎版本 |
| 观赛 | HTML 回放，逐回合播放 |

在这个约束下，**游戏设计的第一目标不是“像原作”，而是“让算法成为胜负主因”**。

## 2. 为什么是回合制

实时操作会让执行层（反应、手速）压过决策层，在 CPU 预算下选手也难以稳定实现。因此统一采用：

- 一步 = 各方同时或轮流下令；
- 引擎按固定顺序结算；
- 所有动作可序列化、可回放、可逐步调试。

## 3. 六条设计原则

1. **保留决策骨架，删掉执行噪音。** 如果一条规则让“手更稳”比“决策更好”更重要，就删掉它。
2. **一个 bot 控制多个单位。** 多单位才能考协同；单单位容易退化成单兵脚本。
3. **部分信息必须由引擎裁剪。** 引擎不能把全图发给 bot 再要求它“假装看不见”；回放可以有上帝视角，选手 API 不能。
4. **要有强制进攻的时钟。** 没有时钟的对战游戏，最优解常是互蹲。时钟须可见、不可逆、有惩罚（P01 用涨水）。
5. **确定性是硬要求。** 模拟层只用整数/定点；随机全部来自带 seed 的 RNG；遍历顺序固定；不用系统时间、线程、网络、文件；同 seed + 同动作必须得到逐字节相同的状态。
6. **动作空间可搜索、可脚本、可学习。** 提供 helper（视线、寻路、弹道模拟等），但不提供“答案”。

## 4. 什么算一个好题目

- 一句话能讲清；规则可手算；
- 策略有层次，信息和资源都有取舍；
- 有硬时钟，不进攻会输；
- 随机性可控（地图、出生点可随机，结算尽量确定）；
- 输的时候能解释“哪一步、哪个决策”；
- 回放能看懂；
- 20–30 个边界用例能覆盖大部分规则歧义。

要谨慎的题目：纯反应类、纯随机类、纯数值类、完全信息且无时钟、依赖未定点化连续物理、单位太多需要逐个微操。

## 5. 常见失败模式

| 失败模式 | 对策 |
|---|---|
| 互蹲 / 拖时间 | 硬时钟 + 不可逆目标；平局 tiebreak 不奖励刷数据 |
| 雪球 | 重生、追赶机制、优势方承担风险 |
| 随机性主导 | 战斗结算确定；地图镜像；座位轮换；多局制 |
| 执行技巧主导 | 回合制；瞄准离散化；预算内允许搜索 |
| 信息泄漏 | 引擎只构造本方可见状态；bot 独立子进程；公开头文件不含完整状态；`pack.py` + `leakcheck.py` + red-team |
| 非确定性 | 禁浮点、禁 `unordered_*` 影响结算、固定 RNG 实现、跨平台 hash 对账 |
| 基准太强或太弱 | 多档基准互打校准，目标是“认真写的选手能稳定击败入门档”，不是“稳赢所有档” |
| 规则歧义 | 结算顺序编号；每个歧义一条裁定；golden 用例；规则变更 bump 版本和 hash |

## 6. 成功标准

一道题可以上线（`playtest` 之后）至少满足：

- 规则一页纸能讲清，边界用例有明确答案；
- 引擎 fuzz 无崩溃，同 seed hash 一致；
- 选手 API 不含隐藏状态，`leakcheck` 通过；
- 基准档位可区分，地图/座位偏差在可接受范围；
- 计时有余量，超时判罚明确；
- 回放可逐帧重算；
- 文档、选手包齐全，私有文件不在包内。

逐项清单见 [acceptance.md](acceptance.md)。
